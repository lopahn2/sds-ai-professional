# 복합 장애 비교 시험 세트 (LiveProbe 대 단일 모델)

## 목표와 범위 (2026-11-26 소유자 지시)

LiveProbe가 단일 모델 하나로 처리할 때보다 우수함을 보이는 시험 장애 세트를 만든다. 평가 우선순위는 비용이 1순위, 시간이 2순위다.

LiveProbe는 RAG로 지난 장애의 유효한 해결 방법을 찾을수록, 다음 장애의 해결 비용이 줄어드는 구조를 목표로 한다. 이 세트는 그 효과도 측정할 수 있어야 한다.

조건은 다음과 같다.
- Kubernetes 장애와 애플리케이션 장애를 합친 복합 장애여야 한다.
- 애플리케이션 장애는 커넥션 풀 누수 같은 인프라 수준이어야 한다.
- 시험은 3개다.
- 난이도: Terra xhigh에 장애 로그와 "장애를 해결하라"는 프롬프트 하나만 주면 해결에 실패해야 한다.

범위에서 뺀 것은 다음과 같다.
- LiveProbe 제품 코드 변경. 답이 담긴 런북을 RAG에 추가하는 것도 빼서, 시험에 맞춘 튜닝을 막는다.
- dev 클러스터에 직접 장애를 주입하는 것. Codex의 동일 조건 비교가 같은 dev와 노드 자원을 쓰는 중이다.

## 완료 기준

1. 세 시험 각각이 다음을 갖춘다.
   - 원인 사슬: Kubernetes 원인과 애플리케이션 인프라 원인을 모두 포함한다.
   - 공개 입력과 정답표의 분리
   - 조치 기본 동작(primitive)
   - 일정 시간 부하를 건 뒤의 정상 여부(soak)로 내리는 복구 판정
   - RAG 반복 회차
2. 공개 로그 묶음은 실제 프로세스가 남긴 로그로 만든다. 시험 장치 이름은 묶음에 나타나지 않는다(렌더러가 차단한다).
3. 시험마다 Terra 6.1 xhigh 단일 프롬프트 실행 결과와 비용을 기록한다. 그 답의 조치를 재현 환경에 그대로 적용해 soak에서 실패하는지 확인한다.
4. 정답 조치는 같은 재현에서 soak를 통과한다. 해결이 가능한 문제임을 보이기 위해서다.
5. 측정 지표, 반복 회차 구성, LiveProbe가 갖춰야 할 근거 수집과 남은 위험을 이 문서에 기록한다.

## 설계 원칙

기존 사례표(F1~F4, N1~N4)는 모두 원인이 하나다. 2026-11-26 동일 조건 비교에서도 단독 모델이 해결했다. 그 비교에서 단독 모델은 20~65초, $0.015~0.25로 복구했다.
- KW-03 PVC 참조
- 주문 이미지 계약
- 풀 설정

그래서 이 세트는 단독 모델이 증상만 고치고 실패하도록 설계한다.

- **두 층의 원인:** Kubernetes 쪽 원인과 애플리케이션 인프라 쪽 원인이 함께 있다. 하나만 고치면 soak에서 다시 무너진다.
- **로그에 없는 결정적 근거:** 로그에는 증상만 남는다. 원인을 가리는 근거는 Kubernetes 객체 상태, 변경 이력, 메트릭, 소스에 있다. LiveProbe는 이를 수집하고 단독 모델은 받지 못한다.
  - Kubernetes 객체 상태: probe 경로, EndpointSlice, Pod resources
  - 변경 이력
  - 메트릭: Hikari active, CPU throttling
  - 소스
- **그럴듯한 오답과 미끼:**
  - 최근 배포
  - 재시도 증폭
  - 백업 Job의 복제 지연 경고
  - 설정 변경으로 인한 재시작
  - 이런 단서를 따라가 롤백, 재시작, 풀 확대, 타임아웃 조정을 하면 soak에서 실패한다. 일부 조치는 안전 위반이다(옛 primary 쓰기 허용 → split brain).
- **판정은 실행 결과로:** 답의 문장이 아니라, 답이 제시한 조치를 재현 환경에 그대로 적용한 뒤 soak 통과 여부로 해결을 판정한다.

## 세 시나리오

공통 대상은 다음과 같다. 소스는 `evaluation/compound/fixture`에 있다.
- `shopfront` Spring Boot 3.5.16 하나의 JAR가 두 역할을 한다.
  - `stock`: PostgreSQL 17, Hikari
  - `order`: 재고 호출, 즉시 재시도 3회
- 평상 부하는 web 6 rps와 partner 0.25 rps다(C3는 web 10 rps).
- DB 역할 `shop_app`은 연결 상한 8이다.

### C1 커넥션 누수가 DB 결합 liveness에 가려짐

| 구분 | 내용 |
| --- | --- |
| 애플리케이션 원인 | `PartnerLedger`(1.4.2)는 연결을 직접 얻고 `SQLException`일 때만 정리한다. 파트너가 할당을 동결(HOLD)하면 비검사 예외 `PartnerAllocationHeld`가 정리 코드를 건너뛴다. 그래서 연결이 열린 트랜잭션째 풀로 돌아오지 않는다. |
| Kubernetes 원인 | liveness probe가 DB 검사를 포함한 `/actuator/health`를 본다. 풀(4개)이 고갈되면 probe가 시간 초과로 실패하고 kubelet이 재시작한다. 재시작이 누수 연결을 풀어 주므로 누수가 "재시작 반복"으로 가려진다. |
| 계기 | 배포 없이 3분 주기 CronJob `partner-feed-sync`가 HOLD 상태를 데이터로 기록한다. |
| 미끼 | T0 80초 전의 무관한 order 롤아웃, order의 즉시 재시도 3회 |
| 로그에 없는 결정적 근거 | 누수 경로 소스, Hikari active 단조 증가, probe 정의 |
| 오답이 실패하는 이유 | liveness를 고치면 재시작이 멈춘다. 그러면 누수가 그대로 쌓여 풀이 영구 고갈된다. 재시작, 풀 확대, 타임아웃 조정, DB 유휴 트랜잭션 종료로는 Hikari가 잃어버린 연결을 되찾지 못한다. |
| 정답 조치 | 1.4.3 패치(해당 경로에서 롤백 후 반환) 또는 partner ledger 경로 비활성화 |

### C2 장애 조치 후 DB Service가 옛 primary를 계속 고름

| 구분 | 내용 |
| --- | --- |
| Kubernetes 원인 | 정기 switchover Job이 `stock-db-0`을 읽기 전용으로 격리하고 `stock-db-1`을 실제로 승격했다(스트리밍 복제, `pg_promote`). 그러나 `stock-db-0`의 라벨 `role=replica` 변경이 쓰기 충돌로 실패했다. Job은 "300초 뒤 재시도"라고만 남기고 끝났다. 그래서 Service `stock-db`가 두 파드를 모두 고른다. |
| 애플리케이션 원인 | 전환 전에 열린 Hikari 연결은 `stock-db-0`에 남는다(maxLifetime 30분). SQLState 25006으로는 연결이 퇴출되지 않는다. 새 연결도 절반은 옛 primary로 간다. |
| 미끼 | 직전 백업 Job의 "replica replay lag 1.2 s" 경고 |
| 로그에 없는 결정적 근거 | Service EndpointSlice와 파드 라벨 |
| 오답이 실패하는 이유 | stock 재시작이나 maxLifetime 단축은 실패를 다시 섞을 뿐이다. 옛 primary의 쓰기 차단을 풀면 오류는 사라지지만 primary 두 개(split brain)가 되므로 안전 위반으로 실패한다. |
| 정답 조치 | `stock-db-0`을 Service에서 빼고(라벨 또는 selector 수정) 그 뒤 stock 풀 재생성. 순서가 중요하다. |

### C3 네임스페이스 기본 CPU 한도가 재시작 때 붙음

| 구분 | 내용 |
| --- | --- |
| Kubernetes 원인 | 아침에 생긴 LimitRange(기본 cpu limit 250m)가 있다. 로그 레벨 ConfigMap 수정으로 Reloader가 stock을 롤링했고, 새 파드가 이 기본 한도를 받았다(이전 파드는 무제한). |
| 애플리케이션 원인 | 행 잠금과 풀 연결을 쥔 채 할당 계획을 계산한다. CPU 제한으로 처리 시간이 4배 이상 길어져 처리량이 평상 부하 아래로 떨어진다. 평일 1.5배 트래픽 구간과 order 즉시 재시도가 과부하를 키운다. |
| 미끼 | ConfigMap 변경과 롤링, 재시도 증폭 |
| 로그에 없는 결정적 근거 | 새 파드의 resources.limits.cpu, CPU throttling 지표, LimitRange 객체. 어떤 로그에도 CPU나 LimitRange라는 말이 없다. |
| 오답이 실패하는 이유 | 롤백과 재시작은 다시 기본 한도를 받는다. scale-out은 세 번째 복제본에서 역할 연결 상한(8)에 걸린다. 풀 확대는 CPU를 늘리지 못한다. 재시도와 타임아웃 조정만으로는 처리량이 부족하다. |
| 정답 조치 | stock Deployment에 장애 전 용량에 맞는 명시적 CPU 한도(2000m)를 지정해 네임스페이스 기본값을 덮어쓴다. 동시에 order 재시도를 백오프로 완화한다. 실측 결과 CPU만 고치면 새 파드가 재시도 폭주 속에서 콜드 스타트해 수 분 늦게 회복하므로 soak를 통과하지 못한다. |

## 비교 프로토콜

### 방식

- **단독 모델 (사용자 정의 기준선):** Terra 6.1 `xhigh`에 공개 로그 묶음과 프롬프트 하나("이 장애를 해결하라" + 답 형식)를 준다.
  - 세션 조건: 새 격리 홈, 저장소 밖 빈 작업 폴더, 읽기 전용 샌드박스, 도구 기능 전부 비활성화, 저장소 지침·RAG·LiveProbe 접근 없음
  - 실행기: `evaluation/compound/baseline.py`
  - 시험 장치가 답에 담긴 실행 가능한 조치를 그대로 적용하고 soak로 판정한다.
  - 실패하면 그 결과까지 담은 새 로그 묶음으로 새 세션에서 다시 시도한다. 최대 3회다.
- **LiveProbe:** 같은 시나리오를 dev에 배포해 자체 감지, 분석, 허용 조치와 인계로 처리한다.
  - 인계에 구체적 조치가 있으면 시험 장치가 그대로 실행하고, 같은 soak로 판정한다.
- **(참고) Sol 6.2·Astra 6.2 `xhigh` 단독:** 같은 묶음과 같은 프롬프트로 실행한다. 모델을 키우면 풀리는지 보려는 것이다.

### 지표 (비용 1순위, 시간 2순위)

| 지표 | 정의 |
| --- | --- |
| 해결 장애당 비용 | 회차 전체 모델 비용 ÷ soak를 통과한 회차 수. 해결 0건이면 정의되지 않음(∞)이며, 그 지출은 낭비 비용으로 따로 표시한다. |
| 회차 비용 | 해결 또는 포기까지의 모든 호출 비용. 단독 모델은 시도 전부를 합친다. 단가는 고정 표 `single_baseline.py` 2026-11-23을 쓴다. |
| 지속 복구 시간 | 주입부터 soak 통과까지. 미해결은 30분에서 절단한다. |
| 품질과 안전 | 원인 적중(필수 원인), 안전 위반(옛 primary 쓰기 허용, 공유 DB 상한 상향 등) 건수 |

### RAG 반복 회차

LiveProbe RAG는 `resolved`로 닫힌 사건만 `past_incident`로 색인한다(`rag_ingest.closed_incident_documents`). 지문이 `eval/%`인 사건은 제외되고, 한 질의에 과거 사건은 1건까지만 들어간다.

그래서 회차 사이 조건은 다음과 같다.
- E1이 해결되어 닫혀야 한다.
- 시험 사건에 `eval/` 지문을 쓰면 안 된다.
- 답이 담긴 런북을 미리 넣으면 안 된다.

| 계열 | E1 (냉시작) | E2 (같은 기전, 다른 표면) | E3 |
| --- | --- | --- | --- |
| C1 | partner HOLD 경로 누수 + liveness 결합 | 다른 경로(바우처 만료 비검사 예외)에서 같은 누수 + readiness 결합(재시작 없이 endpoint 이탈) | 정기 정산 작업 경로의 누수 + startupProbe·liveness 결합 |
| C2 | 라벨 충돌로 옛 primary 잔류 | RBAC 거부로 라벨 변경 실패, 다른 서비스 | 노드 drain에 의한 장애 조치 후 같은 잔류 |
| C3 | LimitRange 기본 CPU 한도 | 같은 정책의 기본 memory 한도(GC 지연) | ResourceQuota 도입 후 기본값 적용 |

가설이 맞다면 다음과 같이 나와야 한다.
- LiveProbe의 회차 비용이 E1 > E2 ≥ E3로 줄어든다.
- 단독 모델은 기억이 없으므로 매 회차 같은 비용으로 같은 실패를 반복한다.

현재 제품 구조에서는 RAG 적중이 라우팅이나 그룹 선택을 바꾸지 않고 근거로만 전달된다(`engine._rag`, `router.py`에는 RAG 입력 없음). 그래서 비용 감소는 호출 수, 재시도, 승격이 줄어드는 만큼만 나타난다. 이 세트는 그 한계를 그대로 측정한다.

## 판정 규칙 (단독 모델)

- 답에서 무조건 실행하도록 제시한 조치만 그대로 적용한다. 새 관측(kubectl get, SQL 조회 등)을 전제로 한 조건부 단계와 "조사 후 수정"은 도구가 없는 방식이 스스로 결정한 것이 아니므로 실행하지 않는다.
- 이 규칙만으로 결과를 정하지 않도록, 조건부 단계를 정직하게 수행했다면 풀렸을지도 함께 적는다.
  - 조건이 로그만으로 판단 가능했고 그 조건이 참이었다면 "실질적 해결"로 기록한다.
  - C2 v1이 여기에 해당한다(아래).
- 1차 규칙 채점(`grade.py`)은 선별용이다. 조치 대응 정규식은 조사 문장까지 잡아 과대 집계한다. 최종 대응은 답을 읽고 기록하며, soak 결과로 판정한다.
