# 🛰️ LiveProbe 통합 장애 관제

2026-11-20 · 소유자 설계 승인 · 구현·검수

## 목표와 현재 상태

한 운영자가 한 제품, 한 사건 안에서 서비스 위험과 개입 필요 여부를 동시에 판단한다. 착수 당시 두 API·DB가 분리되어 있었고, 첫 화면에서는 사건 카드 아래로 내려가야 서비스 지도를 볼 수 있었다. 역할 인증, 기존 운영 이력, PR 사람 병합, dev/prd 실행 계정 분리, 현행 모델과 원본 로그 보호를 이어받는다.

## 기능과 메가 프로세스

| 구간 | 행동 주체 | 완료 근거 |
|---|---|---|
| 관측 | 수집기 | 소스 위치로 연결된 로그·Prometheus 메트릭·K8s 이벤트. 태그로 시스템·서비스·환경 식별. 미식별/미관측 구별 |
| 판단·분석 | 분류·추론·검증 에이전트 | 난이도, 그룹·역할과 모델, 독립 검증, 실측·RAG 인용·승격 이유 |
| 수정·복구 | 코드 실행기·인프라 실행기 | 순수 인프라 허용 조치 또는 코드 수정. 복합 원인은 코드 수정 후 인프라 수정 |
| dev QA | QA 실행기 | 개발자 컨트롤러 통합 테스트로 업무 흐름·기대 결과 식별. 실제 dev UI를 브라우저로 조작해 최종 상태까지 확인. 필수 테스트가 없으면 알림 후 AI가 저장소에 테스트 추가·재배포 |
| 승인 | prd 승인 권한을 가진 운영자 | 최신 QA 단계·증거와 prd 변경 영향·보존 방법·복구 검증을 그림으로 검토. 파괴적 변경의 근거 부족 시 승인 차단 |
| prd 복구 확인 | 배포 실행기·관제 시스템 | 사람 병합과 승인 버전 일치, 배포 성공 후 복구 확인 대기. 원래 오류에 대응하는 성공 관측 또는 허용된 무해 점검 후 해결 |

모든 단계에서 보완 요청 가능. 같은 사건에서 dev 반영·실제 UI 재검증·재승인한다. 이전 회차 결과와 승인 지문은 이력으로 보존한다. 승인 후 진행 중인 변경은 안전 경계에서 조정하며 부작용을 중복 적용하지 않는다.

## 화면 설계

- 홈 중앙은 처음부터 전체 서비스 지도. 시스템별 그룹 내 서비스 하나에 dev/prd 표시. 독립 서비스 및 정상 시스템 유지, 서비스와 상위 그룹에 위험 아이콘·텍스트. 개입 목록을 옆에 두고 환경·서비스별 1건은 사건으로 직행, 여러 건이면 해당 목록. 우측 상단 종으로 새 장애·QA 보완·승인 안내. 새 이벤트는 화면/선택/배율을 바꾸지 않는다.
- 통합 사건 목록·지도·건수는 같은 사건 상태 사용. 운영 승인은 목록 필터로 이동. 인프라·애플리케이션·운영 승인은 업무 구분이며 역할과 별도 사이트로 분할하지 않는다. 기존 역사 원본 ID·출처 보존.
- 관제실의 가로 메가 단계와 현재 단계의 에이전트 도식/병렬 분기 중심. 실제 실행과 선택한 과거 노드 구분. 짧은 결론·근거·다음 행동은 옆, 긴 공개 답변·원문은 선택 시 넓게 열고 복귀. 두 화면 크기에서 첫 판단·단계 요약에 중첩 스크롤 제거. Naria 모션과 동작 줄이기.
- QA 절차 그림과 prd 위험 영향 그림에는 단계 선택 상세·확인 불가/실패/미실행 구분. 과거 근거를 생성하지 않는다. 소스 위치 등록/수집 상태와 모델 정책은 설정, 비교 평가·집계는 검토 기록.

## 담당 범위와 검수 순서

1. 실제 사건을 읽어 1440×900·1920×1080 화면과 흐름을 점검한다.
2. 기존 root 사건 모델과 Application API를 연결해 동일 호스트로 제공한다. 권한 분리, 외부 실행기 pull, 과거 DB·데이터 보존.
3. 소스 어댑터 및 상태 판정에서 선택자 없는 대상, 의도한 단독, 준비된 백엔드 부재, 미관측, 실패 요청을 구분한다.
4. 코드·인프라·실제 UI QA·보완·승인 및 배포 후 복구 확인을 정상 API·worker·화면 진입점에서 연결한다. 실패·중복·재시작·비동기 도착·과거 기록 검증.
5. 격리 DB와 브라우저로 실제 사용자 여정을 검증하고 확인된 변경을 로컬 관제에 반영한다. 기존 부트스트랩과 서버 상태를 대조하고 운영 이력 보존. 실제 prd 업무 변경, 실결제, 인위적인 운영 장애 주입은 시험하지 않는다. 검증하지 못한 항목은 근거와 함께 기록한다.

## 진행

- 소유자 인터뷰·설계 승인 완료. 현행 기준 작업본의 미커밋 변경도 입력으로 사용한다.
- 11월 20일 기준선에서 홈 지도는 두 해상도 모두 화면 상단에서 490px 아래 시작했다. 1440×900에서는 서비스명 실효 크기가 약 6.4px였다. 실서비스 GET 응답으로 후보 홈을 열어 1440×900·1920×1080 모두 시스템 4개, 서비스 14개, dev/prd 환경 셀 28개와 옆 개입 목록을 확인했다. 두 화면 모두 가로·세로 넘침이 없었다.
- 격리 FastAPI에 연결한 Chromium에서 같은 두 화면 크기로 병렬 에이전트 선택 고정, 공개 답변 갱신, QA·승인 대기 이동, 940px 상세 창을 닫은 뒤 포커스 복귀, 저장된 Application 사건의 원래 번호 직행을 확인했다. 승인 대상과 원문 조회 권한은 시험용이었다. 기본 단계 요약의 내부 스크롤은 두 화면 모두 0px였다.
- 로컬 수집기에 `system` 라벨을 적용했다. 현재 Pod의 시스템·서비스 라벨은 dev 14/14, prd 9/9였다. 동일 PVC로 Prometheus를 재시작했고 Alloy는 구성 파일을 다시 읽었다. 신규 Prometheus 대상은 dev/prd 각 9개, Loki 최근 시리즈는 dev 13개·prd 27개에서 시스템·서비스를 함께 식별했다. 변경 20분 전의 Prometheus 대상 수도 21로 다시 조회했다.
- 실제 dev 주문 UI에서 상품 `a`와 `x`를 조회해 각각 ‘주문 가능·재고 42’와 ‘등록되지 않은 상품’을 확인했다. 이 측정은 브라우저 실행기 구현 전의 기준 관측이다.
- 전환 전 실제 DB는 K8s 사건 1,474건, 독립 Application 사건 9건(그중 기존 dev 시험 대기 2건)이었다. 폐기 DB와 실제 이전 API 이미지를 사용해 0011 스키마에서 기존 사건을 보존하고 기능을 되돌리는 호환 이미지의 기동·readiness를 시험했다.
- 로컬 4175를 로그인 시 시작하는 서비스로 등록했다. `liveprobe.localhost/incidents/1501`은 같은 번호로, `application.liveprobe.localhost/`는 `127.0.0.1:4175/application`으로 열렸다. 운영 DB는 0011에서 K8s 사건 1,474건·연결 0건이었다. 기존 Application 공개 요약은 같은 호스트에서 200, 개인 권한 없는 원문은 401을 반환했다. 현재 활성화된 경로는 K8s 관제와 기존 Application 이력·dev 시험 확인이다.
- 운영 화면의 연결 확인에서 Kubernetes 대상 23개, Loki 로그 시리즈 31개, Prometheus 대상 18개를 읽었고 셋 모두 환경·서비스·시스템 태그 누락이 0이었다. Prometheus의 해당 실패 대상도 0이었다. 수집 시점에 따라 개수는 바뀐다.
- 실제 dev 업무 화면 5개를 읽기 전용 브라우저 QA로 확인했다. 주문은 상품 존재·부재, 카탈로그는 검색과 상세, 결제는 최근 결제 조회, 알림은 대기 건수, 배송은 지연 목록을 화면·요청 응답·별도 조회와 대조했다. 이 실행은 기존 dev 배포를 대상으로 했으며 prd 배포·사람 승인 이력을 생성하지 않았다.

- 4175에서 운영 사건 #1501의 가로 흐름을 재검수했다. 1440×900에서 전체 보기 제목 최솟값 13.04px, 1920×1080에서 15.68px였고 두 화면 모두 11개 실제 노드와 병렬 분기가 캔버스 안에 있었다. 당시 준비된 서비스 연결 대상 1개와 원인 미확정을 각각 표시한다.
- 실제 dev 서비스 5종의 브라우저 영수증에 있는 36개 기대값·관측값·개발자 테스트 출처를 격리 Chromium에서 확인했다. 해당 이미지와 소스 지문에 묶인 영수증은 제어기 판정을 통과했고, 릴리스 번호만 바꾸면 5건 모두 거절됐다. 이 시험은 운영 승인 및 배포 기록을 추가하지 않았다.
- 격리 브라우저에서 과거 사건의 그룹 구성, 모델 선택, 원인·반대 근거, 승격, 검증, 참고 문서와 사용량을 포함한 P20 검사 15개가 모두 통과했다. 원래 사건으로 들어가는 경로와 개인 세션 범위도 따로 검사했다.

### 재현과 확인 범위

| 경로 | 확인한 결과 |
|---|---|
| 실제 조회 전용 dev 화면 | 주문 12단계, 카탈로그 9단계, 결제·알림·배송 각 5단계. 개발자 시험 파일은 빌드 소스 지문에 고정했고, 실제 DOM과 응답을 업무 기대값에 대조했다. |
| 격리 통합 사건 | 실제 HTTP와 Chromium으로 새 루트 사건을 접수하고 수정 전 시험 실패·수정 후 통과를 관측했다. 사설 시험용 배포 대상에서 dev 적용, 승인, prd 적용 후 원래 요청 복구, 종료 후 후속 메모까지 같은 사건으로 이어졌다. |
| 누락된 필수 시험 | 첫 회차 영수증을 보존하고 새 소스를 수집했다. 격리 모델이 실제 시험 파일을 추가한 경로는 새 이미지로 dev QA를 통과했다. 두 번째 회차에도 시험이 없으면 인계로 종료하고 prd 배포를 생성하지 않았다. |
| 인프라 안전성 | 혼합 원인에서는 dev에서 검증한 인프라 조치 영수증을 소비한다. 응답이 유실돼도 같은 쓰기를 다시 하지 않는 것을 확인했다. 실제 운영에 적용한 Pod 준비 조건으로 인프라 조치 72개 격리 테스트를 통과했다. |

격리 인수 시험 코드는 [코드 조치·QA·복구 시험](../../liveprobe/application_tests/test_console_release_acceptance.py)과 [혼합 인프라 시험](../../liveprobe/tests/test_mixed_remediation.py)에 있다. 외부 Git·모델과 prd 배포는 시험 대역을 사용했다. 실제 dev 5개 서비스의 업무 읽기 검증은 별도로 수행했다.

통합 API 회귀에서 `qa_fix`·`approval`·`recovery`로 조회한 목록과 전체 건수를 대조했다. 같은 운영자 메모를 루트와 Application 원본 두 주소로 접수했을 때 한 건만 저장됐다. CSRF가 빠진 브라우저 요청, 감지 기계 신원, 사건 출처가 어긋난 연결도 거절됐다. [통합 API 시험](../../liveprobe/tests/test_unified_incidents.py)

Application 격리 시험 51건에서 기존 v2 임대의 갱신, v3의 역할별 작업 배정, 역할 없는 v3 임대의 갱신·보고 거절을 확인했다. 누락된 카탈로그 시험은 수정 에이전트의 실제 입력에 등록 경로와 가격·설명·재고 기대가 들어갔고, 시험 파일을 추가한 회차는 Chromium 업무 검증까지 통과했다. [실행기 역할 시험](../../liveprobe/application_tests/test_unified_application.py), [보완 회차 인수 시험](../../liveprobe/application_tests/test_console_release_acceptance.py)

K8s 백엔드 전체 검사는 폐기 PostgreSQL에서 작업 전 1,508개 중 31개 실패, 작업본 1,536개 중 30개 실패였다. 작업본의 실패 30개는 모두 기준선에도 있었다. RAG 생성 열 삽입, 과거 스키마 되돌림, 예전 stg 기대값 등이 포함된다. 전체 통과로 계산하지 않는다. 대시보드 단위 203개와 1440px의 홈·권한·이력 브라우저 회귀 28개는 모두 통과했다.

## 운영자가 보는 사건 흐름과 API 계약

| 운영자가 보는 단계 | 저장·검증 기준 |
|---|---|
| 분석과 수정 | 새 통합 사건은 원래 Kubernetes 사건 번호를 유지한다. 코드 변경, 혼합 원인의 인프라 조치, 실행기 진행 상태를 연결된 Application 기록에서 읽는다. 외부 실행기가 일감을 가져간다. |
| dev 검증 | 기존 `dev-prd/v2` 사건은 당시 사람 시험과 그 영수증으로 진행한다. 새 통합 릴리스는 `dev-qa-prd/v3`를 사용한다. dev 이미지와 prd 계획을 확정한 뒤 QA 작업자는 개발자 시험을 찾아 실제 dev 화면과 업무 응답을 대조한다. |
| 보완 | 업무 검증 실패 또는 확인 불가는 `qa_failed`에 남는다. 운영자는 원인과 실패 단계를 보고 보완 또는 QA 재실행을 요청한다. 필수 시험 파일 누락은 서버가 확인한 파일 경로·시험명·업무 기대값으로 자동 보완 회차를 한 번 연다. 다시 누락되면 운영자에게 인계한다. |

## 로컬 적용 상태

홈과 관제실의 새 화면을 4175에서 제공한다. 1440×900과 1920×1080에서 지도·개입 목록과 실제 사건 #1501을 열어 읽기 크기, 병렬 노드, 화면 넘침을 확인했다. Application 기존 주소에서 원본 사건 번호가 있는 북마크도 같은 번호로 연결했다. [관제 홈](http://127.0.0.1:4175/) · [사건 #1501](http://127.0.0.1:4175/incidents/1501)

## 운영자 관제실 개편 적용
