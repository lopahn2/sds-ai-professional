# LiveProbe 검색·기억 개선과 AutoRAG 루프 (2026-11-27)

## 배경

소유자 지시: LiveProbe의 처음 식별부터 종료까지 흐름에서 개선할 부분을 찾는다. 현재 RAG에 AutoRAG 개념을 적용해 개선 흐름을 넣는다.

### 흐름 진단

운영 DB는 로컬 k3s `liveprobe-system`이다. 2026-11-27에 읽기 전용으로 조회했다.

흐름은 다음 순서로 진행된다.
1. 신호 → 사건
2. 근거 수집(E1~E12)
3. 라우터(SIMPLE/NORMAL/COMPLEX/HIGH_RISK)
4. 그룹 실행 전 복구 관측
5. RAG 검색과 선례 판정
6. 역할 그룹 실행(인용 검사, 독립 검증, 승격)
7. 허용 조치 실행 → 조치 뒤 관측 → `resolved` 또는 인계
8. 운영자 종료(검증된 해결 기록) → 60초 주기 색인 → 다음 사건의 검색

| # | 발견 | 근거 |
| --- | --- | --- |
| ① | 한도 소진 시 사건 예산 끝까지 대기 | C2c 3회 각 약 910초, 모델 호출 0회 |
| ② | 검색 품질을 측정한 적이 없다. 질의와 매개변수가 고정이다. | 검색이 포함된 역할 호출 1,733회 중 전달 1,667회, 실제 인용 60회(3.5%)다.<br>질의는 고정 템플릿 5종이다(이미지 풀, 엔드포인트, OOM, 5xx 호출자, 지연 + 서명).<br>k=3, RRF 60, 후보 30, 선례 Jaccard 0.5는 평가 없이 정한 값이다. |
| ③ | 해결 기억이 쌓이지 않는다. | 엔진이 해결한 운영 사건은 151건이다(조치 동반 43건).<br>그런데 `past_incident` 문서는 0건이다. 요약 허용 어휘 필터가 한국어·자유 문장을 모두 거부한다.<br>검증된 해결은 평가 사건 2건뿐이다. |
| ④ | 선례가 이어지지 않는다. 뒤 단계도 전달되지 않는다. | C2b 2라운드는 조치 뒤 서명이 바뀌어 유사도 0.4로 선례를 잃었다.<br>분석가는 선례의 뒤 단계(pg_hba)를 현재 근거가 없다며 확정 조치에도, 확인 항목에도 넣지 않았다. |

## 합의한 범위 (2026-11-27 소유자 답변)

- **②③④와 AutoRAG 루프를 구현한다.**
  - ① 한도 대기는 바꾸지 않는다. 현행대로 예산 끝까지 대기하고, 다른 공급자로 전환하지 않는다.
- **적용 방식:** AutoRAG가 찾은 구성이 기준을 넘으면 자동으로 적용한다.
- **검증 범위**
  - 단위 시험
  - 운영 DB 읽기 전용 오프라인 평가
  - 로컬 k3s API 반영과 롤백 명령 기록
  - 장애 주입 시험(LiveProbe 실사건 재시험)은 하지 않는다. 보류가 유지된다.
- **경계**
  - 평가 사건(`fingerprint eval/`)은 평가셋에서 뺀다. 정답 키는 질의, 라벨, 문서에 넣지 않는다.
  - 운영 검색은 `eval_memory`를 계속 보지 않는다.

## 설계

### AutoRAG 개념 대응

| AutoRAG 개념 | LiveProbe 구현 |
| --- | --- |
| 평가 데이터셋(QA·corpus) 자동 생성 | 운영 사건마다 당시 증거 행으로 Bundle을 다시 만든다. 라우팅 특징과 합쳐 검색 질의를 재구성한다. |
| 정답 문서(retrieval_gt) | 두 가지를 합친다.<br>① 감지 계열(`family_hint`, 신호 이유)과 문서 메타데이터(`applies_to`, `family`)의 일치. 감지 단계 값이라 검색 구성과 무관하다.<br>② 그 사건에서 실제 인용된 문서.<br>과거 사건 문서는 질의 사건보다 먼저 닫혔고 같은 계열일 때만 정답이다. 자기 문서와 미래 문서는 순위에서 뺀다. |
| 노드별 모듈·매개변수 후보 | 질의 생성(`template`, `findings` 확장), 검색 방식(`hybrid`, `vector`, `lexical`), RRF 계수, 후보 수, k, 과거 사건 상한 |
| 지표 | nDCG@k, 정밀도@k(프롬프트에 넣는 문서 중 관련 비율), hit@k, MRR, 상한 재현율, 지연 |
| 전략(최적 구성 선택) | 목표 = 0.5·nDCG@k + 0.5·정밀도@k. 시간순 앞 70%로 고르고, 뒤 30% 보류셋에서 현행과 비교한다. |
| 최적 구성 배포 | 다음 기준을 모두 넘으면 자동 적용한다.<br>• 보류셋 목표가 현행 대비 +0.02 이상<br>• 보류셋 hit@k 하락 없음<br>• 지연 p95가 현행 대비 1.5배 또는 +50ms 이내<br>• 표본이 학습 20건 이상, 보류 10건 이상<br>적용할 때마다 `settings.rag_retrieval`에 이력을 남기고 감사 로그를 쓴다. 롤백과 중지 명령이 있다. |

### 흐름 개선

- **검색 구성 레코드:** `rag.search`가 구성(방식, RRF, 후보, k, 종류 상한)을 받는다. 기본값은 현행과 같은 순위를 낸다. 실시간 검색과 오프라인 평가가 같은 융합 함수를 쓴다.
- **관측 해결 기억**
  - 조치(허용 유형) 뒤 관측 복구로 `resolved`가 된 운영 사건을 구조화 문서로 만든다(`past_incident`, source `observed-resolution`).
  - 문서는 고정 어휘만 쓴다. 서명, 신호, 계열, 조치 유형 문장, 관측 복구 사실이 들어가고 자유 문장은 없다.
  - 선례 판정에도 쓴다. 다만 COMPLEX→NORMAL 하향은 운영자 검증 해결(`verified-resolution`)만 한다.
- **선례 연속성**
  - 같은 워크로드의 최근 사건(기본 120분)이 쓴 선례는 완화된 임계값(0.25)으로 이어받는다.
  - 이어받은 선례로는 그룹을 하향하지 않는다.
  - 현재 검색이 허용하는 종류의 문서만 이어받는다.
- **선례 확인 항목**
  - 선례의 검증된 단계를 모든 역할 프롬프트의 사건 정보(`precedent_checks`)와 인계에 넣는다.
  - 문구: "현재 근거로 확인하거나 반박하라. 근거가 수집되지 않았으면 확인 단계로 적어라. 선례만으로 조치하지 마라."

## 완료 기준

1. 검색 구성을 설정 레코드로 바꿀 수 있다. 기본 구성은 현행과 같은 결과를 낸다(단위 시험).
2. `findings` 질의 확장은 구조화 관찰과 신호 이름만 쓴다. 라벨성 키(`family_hint` 등)는 쓰지 않는다.
3. 조치와 관측 복구가 있는 운영 해결 사건이 구조화 기억 문서로 색인된다. 평가 사건은 제외한다.
4. 선례 연속성과 확인 항목이 동작한다. 하향은 하지 않고, 허용 종류만 이어받는다(단위 시험).
5. AutoRAG가 운영 DB에서 평가셋을 만들고 모든 후보를 평가한다. 기준 충족 시에만 자동 적용하며, 이력·롤백·중지가 동작한다.
6. 단위 시험이 통과하고, 오프라인 평가 결과와 로컬 k3s 반영·롤백 명령을 이 문서에 기록한다.

## 설계 정정 (오프라인 평가 중, 근거와 함께)

1. **목표를 계열별 평균(macro)으로 바꾸고 계열별 hit 비열등 조건을 추가했다.**
   - 첫 dry-run에서 단순 평균 목표가 `findings/lexical/c60/k2/p2`를 골랐다.
   - 평가셋 498건 중 endpoint_loss가 317건(64%)이라 평균이 이 계열에 지배됐다.
   - 이 구성은 image_crash hit를 0.789에서 0.605로, http_5xx hit를 0.991에서 0.882로 떨어뜨렸다(전체 기간).
   - 정정 후 기준: 계열 평균 목표 + 보류셋 5건 이상 계열의 hit 하락 0.05 이하.
2. **동점 처리:** 현행과 다른 항목이 가장 적은 구성을 고른다. 이전에는 키 문자열 순이라 무관한 매개변수(c60, p2)까지 바뀌었다.
3. **가드를 선택 단계에도 적용했다.** 학습 구간에서 hit 조건을 만족하는 후보 중에서만 최고를 고른다. 이전에는 학습 최고 후보(`findings/hybrid/rrf20/c30/k2/p1`)가 보류셋에서 가드에 걸려 그냥 현행 유지로 끝났다.

세 정정 모두 적용을 더 어렵게 만드는 쪽이다. 결과를 적용 쪽으로 맞추려고 기준을 느슨하게 한 정정은 없다.

4. **선례 통로를 문서 통로에서 분리했다(v11·v12).**
   - **무슨 일이 있었나.** v10 반영 뒤 첫 예약 실행(06:04:58 UTC)이 `template/vector/c60/k3/p0`을 자동 적용했다.
     - 보류셋 계열 평균 목표: 0.4293 → 0.4806
     - hit: 0.62 → 0.7333
   - **원인.** 관측 해결 문서 43건이 문서 상위 k에 섞였다. 대부분 image_pull이라 다른 계열에는 잡음이었다. 조정기는 과거 사건 상한 0으로 이 잡음을 없앴다.
   - **부작용.** 운영자 검증 선례도 같은 `past_incident`라서 선례 통로까지 꺼졌다.
   - **고친 내용**
     - 문서 통로(런북·공개 문서·참고 가이드)만 AutoRAG가 조정한다. 탐색 공간은 48개다.

     - 선례 참조에는 문서의 모든 청크를 넣는다. 그래야 두 청크로 나뉜 검증 단계가 확인 항목으로 전달된다.
   - **정리.** `p0` 구성은 `python -m app.rag_tuning reset`(이력 기록)으로 되돌렸다. 고친 버전으로 다시 돌린 실행은 현행을 유지했다(아래).

5. **쌓인 운영 사건을 모두 평가셋에 넣었다.** 소유자 질문 "이미 쌓여있는 Rag 데이터를 AutoRag로 넣으면 안돼?"를 받고 바꿨다. 근거는 아래 "누적 운영 데이터 전량 투입"에 있다.
   - **평가셋 상한 600건을 없앴다.** `DATASET_LIMIT` 600 → 5000이다. 최신 600건만 읽어서 2026-09-25~10-26의 운영 사건 728건이 빠져 있었다.
   - **계열 힌트가 없으면 신호 이름으로 계열을 정한다.** 감시기 분류(`incidents.REASON_CLASS`)에 OOM이 없다. 그래서 OOM 사건에는 `family_hint`가 하나도 없었다.
     - 이런 사건은 자기 신호 이름(`SIGNAL_FAMILY`)으로 계열을 정한다. 표는 감시기 분류를 그대로 옮기고 `TargetWorkloadOOMKilled`, `OOMKilled`, `TargetWorkloadCrashLooping` 세 개만 더했다.
     - 시험이 표와 감시기 분류가 같은지 확인한다.
   - **시간 분할을 계열마다 한다.** 각 계열에서 오래된 70%로 학습하고 최신 30%를 보류한다. 전체를 한 번에 시간순으로 자르면 OOM 사건이 모두 학습 쪽에 들어가서, 보류셋 가드가 OOM을 볼 수 없다.
   - **바꾸지 않은 것:** 최소 이득, 계열 hit 허용치, 작은 그룹 기준, 지연 상한. 데이터만 늘렸고 판정 기준은 손대지 않았다.

6. **계열별 순위 가드를 더했다(v13).** 소유자 지시 "(3)을 하고"에 따른 것이다. 바로 위 평가에서 http_5xx는 hit가 그대로였지만 관련 런북이 1위에서 2위로 밀렸다(목표 0.691 → 0.610). 그런데 hit만 보는 가드는 이를 통과시켰다.
   - **규칙:** 보류 5건 이상인 계열은 목표(0.5·nDCG + 0.5·정밀도)가 `OBJECTIVE_TOLERANCE` 0.05보다 더 떨어지면 안 된다. 선택 단계(학습 구간)와 확인 단계(보류셋)에 모두 적용한다.
   - **결과:** 이 가드를 넣으면 48개 후보 중 기준을 통과하는 것은 현행 구성(`c30`/`c60`)뿐이다. 현행 구성이 유지된다(근거는 아래 "v13").

### 운영 DB 대조와 오프라인 평가

- **방법**
  - liveprobe-api Pod 안에서 새 모듈을 메모리에만 적재했다. 배포 전이다.
  - 읽기 전용이다. 평가(dry-run)는 설정을 쓰지 않는다.
  - Pod 메모리 최고치는 1,215Mi다(한도 1,536Mi).

### Codex 작업 트리와 병합 (2026-11-27)

- **병합이 필요했던 이유.** `rag.py`, `engine.py`, `main.py`, `evalrun.py`는 Codex가 작업 중이었다. 그래서 AutoRAG 변경을 커밋에만 넣었고(index-only), 작업 트리 파일에는 빠져 있었다.
- **병합 방법.** Codex 파일 159개마다 어느 커밋 판을 기준으로 고쳤는지 찾았다. 기준이 HEAD가 아닌 5개만 3-way 병합했다.
  - `evalrun.py`: 충돌이 없었다.
  - `rag.py`: Codex의 한 번에 도는 검색 SQL과 질의 벡터 캐시는 그대로 두었다. 그 위에 `mode`·`rrf_k`와 공통 `fuse`/`diversify`를 얹었다. 결과 행을 벡터·어휘 순위 목록으로 바꿔 오프라인 평가와 같은 함수로 순위를 매긴다.
  - `engine.py`: Codex의 `_remember_analysis`에 인계 `retrieval`·`precedent_checks`를 합쳤다. Codex가 엔진 질의에 넣은 Istio 문구는 `rag_query.template_query`로 옮겼다.
  - `main.py`: Codex의 임베딩 유휴 해제 루프에 관측 해결 기억 적재를 합쳤다.
  - `incident_counts.py`: 기준을 잘못 찾은 경우였다. Codex의 새 구현(코드 조치 연결 반영)을 그대로 둔다.
