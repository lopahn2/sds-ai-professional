# P20 · naria 디자인 시스템 기반 대시보드 리뉴얼 (1차)

- 대상: `dashboard/` (LiveProbe K8s 관제 화면). 백엔드·실행 권한·인증·클러스터 구성은 범위 밖이다.
- 기준 디자인 시스템: `lopahn2/naria-design-system` main(`d536b75`, 컴포넌트 84개). 디자인 시스템 자체는 수정하지 않는다.
- 작업 브랜치: `renewal/naria-design-system`.
- 요청 요지(2026-11-14): 디자인만이 아니라 UX가 가장 중요하다. 어떤 시스템인지 이해하고, 운영자가 들어와서 데이터를 보고 → 대응하고 → 확인하는 흐름을 기준으로 정리한다.

이 문서는 `AGENTS.md`에 따라 범위·완료 기준·진척·검증 근거를 기록한다. 별도 인터뷰 없이 사용자의 직접 지시로 시작했으므로, 아래 "판단" 항목은 작업자가 정한 것이며 사용자 확인 전이다.

## 1. 시스템과 운영자 흐름

LiveProbe는 Kubernetes 이상 신호를 사건으로 묶고, 난이도·위험도에 따라 AI 에이전트 그룹이 분석한 뒤 **허용된 조치만 실행하거나 운영자에게 넘기는** 시스템이다. 운영자가 화면에서 하는 일은 네 단계다.

| 단계 | 운영자의 질문 | 화면 | 운영자의 행동 |
| --- | --- | --- | --- |
| 1. 파악 | 지금 문제가 있는가? 내가 결정할 것이 있는가? | 운영 관제 `/` | 대응 대기열 확인, 지도에서 위치 확인 |
| 2. 선별 | 어떤 장애부터 볼 것인가? | 운영 관제 대기열, 알림 버튼, 장애 관제 `/incidents` | 승인·인수 대기 → 조치 중 → 분석 중 순으로 진입 |
| 3. 대응 | AI가 무엇을 근거로 무엇을 하려는가? 승인해도 되는가? | 장애 관제실 `/incidents/:id` | 조치 승인·거절, 인계 인수, 후속 지시, 종료 |
| 4. 확인 | 실제로 복구됐는가? 기록은 남았는가? | 관제실 처리 결과, 검토 기록 `/ledger` | 결과·검증 확인, 재발 여부 확인 |

운영자 결정이 **없으면 멈춰 있는** 상태는 두 가지뿐이다: `action_pending`(조치 승인 대기)과 인수되지 않은 `handed_off`(운영자 인계). 나머지 진행 상태(`open`·`analyzing`·`acting`)는 AI가 스스로 진행한다. 이 구분을 화면 전체의 우선순위 기준으로 삼는다(`dashboard/src/responseQueue.ts`).

## 2. 리뉴얼 전 UX 문제 (모의 API 1440×900 캡처 기준)

1. **첫 화면이 "내 차례인가"에 답하지 않는다.** 운영 관제 상단의 `진행 중 / 승인 대기 / 미인수 이관`이 서버 집계가 없으면 모두 `미관측`으로 크게 표시됐고, 진행 중 장애는 상태만 있는 한 줄이라 무엇을 해야 하는지 알 수 없었다.
2. **알림·목록이 수준(심각도) 순이다.** 승인을 기다리며 멈춰 있는 단순 장애가 AI가 분석 중인 고위험 장애보다 아래에 놓였다.
3. **장애 목록의 빠른 필터가 끝난 결과뿐이다.** `자동 복구 / 운영자 종료 / 처리 실패 / 운영자 이관`만 있고 `승인 대기`·`분석 중`은 접힌 상세 필터 안에 있었다. 행에서도 운영자 결정이 필요한지 구분되지 않았다.
4. **관제실의 다음 할 일이 약하다.** `다음 …` 한 줄이 12px 보조 문구였고, 결정 카드(승인·인수)는 대화 영역 안에서 직접 찾아야 했다.
5. **시각 언어가 제각각이다.** 메뉴 아이콘이 문자(▦ ◎ ☷ ⚙)였고, 색·곡률·서체가 디자인 시스템과 달랐으며, 디자인 시스템이 쓰지 않는 보라색이 다이어그램에 있었다.

## 3. 1차 범위와 판단

### 3.1 디자인 시스템 연결

- `@naria/ui` 1.0.1을 `dashboard/vendor/naria-ui-1.0.1.tgz`로 포함하고 `file:` 의존성으로 설치한다(레지스트리 미게시). `Dockerfile`은 `npm ci` 전에 `vendor/`를 복사한다. 실행 의존성 `@radix-ui/react-icons`(디자인 시스템의 peer)가 추가된다.
- `main.tsx`에서 `NariaProvider`(light, modern)로 앱을 감싸고 `@naria/ui/styles.css`를 불러온다.
- `src/naria.css`가 기존 스타일 변수(`--text`, `--accent`, `--line` …)를 디자인 시스템 토큰(`--nds-*`)에 연결한다. 기존 화면의 마크업과 클래스는 유지하므로 화면 계약(DESIGN.md)과 기존 시험의 선택자는 그대로다.
- 서체는 디자인 시스템의 Wanted Sans(내장)로 바뀐다. 다이어그램 작업면은 디자인 시스템 다크 토큰 값으로 맞추고 보라색(경로 변경·이벤트 연결)은 청록으로 바꿨다.

**서체 내장(사용자 결정, 2026-11-14):** 디자인 시스템 CSS가 서체를 내장하고 있어 CSS 번들이 약 45 kB → 약 1.9 MB(gzip 약 1.3 MB)로 커졌다. 사용자가 "서체를 내장할 수 있도록 규칙을 변경한다"고 결정했고, `dashboard/DESIGN.md`의 "웹 폰트 없음" 규칙을 "번들 내장 서체 허용, 실행 중 외부 글꼴 요청 없음"으로 바꿨다.

**디자인 시스템과의 관계(사용자 결정, 2026-11-14):** 디자인 시스템은 초기 세팅용이다. 포함한 패키지 파일은 시작 시점의 사본이며, 이후 변경은 이 대시보드가 스스로 한다. 디자인 시스템 저장소와 계속 맞출 의무는 없다.

### 3.2 UX 변경

| 화면 | 변경 | 사용한 디자인 시스템 컴포넌트 |
| --- | --- | --- |
| 공통 틀 | 메뉴 아이콘을 Radix 아이콘으로 교체. 분석 계정·환경 상태를 점+문구로 표시. 알림 목록을 "대응 필요 먼저" 순으로 정렬하고 항목마다 짧은 다음 행동을 표시. 알림 버튼은 운영자 결정이 필요할 때만 경고색 | `StatusIndicator` |
| 운영 관제 | 상단 "장애 현황"을 **"지금 대응할 일"**로 교체: 한 줄 상황 문장, `승인 대기 / 미인수 이관 / 진행 중` 집계, 대응 순서로 정렬한 장애 카드(다음 행동 배지·위치·수준·경과). 집계는 서버 값 우선, 없으면 완전히 조회된 실시간 목록에서만 계산, 그것도 없으면 `미관측` | `Badge`, `StatusIndicator` |
| 운영 관제 보조 영역 | 노드·CPU·메모리를 미터로 표시(75% 경고·90% 위험, 값이 없으면 미관측). 원천 상태를 점+문구로 표시 | `Meter`, `StatusIndicator` |
| 장애 관제 | 운영자 결정이 필요한 장애가 있으면 목록 위에 바로가기 띠 표시. 빠른 필터를 `전체 · 대응 중(승인 대기/운영자 이관/분석 중) · 처리 결과(자동 복구/운영자 종료/처리 실패)`로 재구성. 결정이 필요한 행에 `승인·거절 필요`/`인수 필요` 표시 | — (토큰만) |
| 장애 관제실 | 결정이 필요한 상태에서는 "다음" 줄을 **"지금 할 일" 띠**로 강조하고 `승인 카드로 이동`/`인계 카드로 이동` 버튼으로 결정 카드까지 스크롤·포커스. 좁은 화면에서는 대화 탭으로 전환 | — (토큰만) |

안전 경계는 바꾸지 않았다: 승인·거절의 명시 확인, 계획 해시, 비밀값 입력, 인수가 변경 허가가 아니라는 안내는 기존 그대로다.

### 3.3 2차: 관제실 내부 (사용자 지시 "관제 내부의 디자인도 모두 바꿔라")

`dashboard/src/room.css`가 관제실 내부 전체의 형태를 디자인 시스템 언어로 다시 정한다. 마크업·클래스·동작은 그대로 두어 승인·지시·비밀값 경계와 기존 시험의 선택자를 유지했다.

| 대상 | 변경 |
| --- | --- |
| 대화 영역 | 흰 바탕 위 흰 카드 → 옅은 회색 바탕 위 흰 카드(그림자 1단계)로 층을 구분 |
| 단계 카드 | 왼쪽 색 띠 제거. 제목 앞 상태 점 + 상태 배지로 표현하고 실행 중 카드는 강조색 테두리·고리. 카드마다 반복되던 `펼치기`·`원문 보기`를 머리 오른쪽 보조 버튼으로 옮겨 카드 높이를 줄임. 본문 14~15px |
| 근거·판단·역할 목록 | 곡률 10px 행, 실패 행은 연한 적색 바탕, 대상은 고정폭 |
| 실행 내용·원문 | 옅은 회색 상자, 고정폭 12px, 시각은 고정폭 |
| 말풍선 | 운영자는 오른쪽 강조 연한색(1차에서 글자가 안 보이던 문제 수정), AI 해석은 왼쪽 중립 표면 |
| 결정 카드 | 전체가 주황이던 카드를 흰 표면 + 경고색 머리 띠로. 종료 카드는 중립 머리 띠. 확인 버튼 높이 44px |
| 운영자 지시 카드 | 번호 붙은 작업 목록, 사전 검사, 경고색 부작용 상자, 확인 영역의 위계 정리 |

| 원문 상세 패널 | 머리·구획 제목·속성 목록·원문 상자 정리 |

| 운영 관제 대기열 카드 | 왼쪽 색 띠 제거, 결정 필요 카드는 연한 바탕색으로 구분 |

### 3.4 3차: 관제실 설명 가능성 (과제계획서 대조 1~9번, 사용자 지시 2026-11-15)

과제계획서는 "어떤 Agents Group Workflow와 모델 조합이 왜 선택됐는지" 설명할 수 있어야 한다고 한다. 엔진은 이 정보를 기록하지만 관제실 기본 화면에 오지 않던 9가지를 보이게 했다.

| # | 계획서 요구 | 변경 | 위치 |
| --- | --- | --- | --- |
| 1 | 역할별 모델·추론 강도 혼합 배치 | 그룹 카드에 역할마다 모델·추론 강도·상태를 **접힌 상태에서도** 표시 | `Explain.tsx` `RoleModels` |
| 2 | 모델 선택 이유 | 수준 판단 카드에 주 분석 모델과 선택 이유(접힘), 후보별 적격·점수·사유 표(펼침) | `ModelChoice` |
| 3 | 결론과 원본 근거의 연결 | 분석 카드에 원인 후보(신뢰도·검증 판정·인용한 근거 번호), 인용 건수와 출처. 인용 원문은 요청 시 표시. 수집되지 않은 근거 번호를 가리킨 인용은 경고 | `AgentBasis`, API `quotes`·`candidates[].evidence_refs` |
| 4 | 상위 모델 승격의 이유 | 승격된 단계와 재실행 단계에 한글 사유와 모델·추론 강도 변화 | `EscalationNote`, API `escalation`·`escalated_from` |
| 5 | 조기 종료 | 그룹 카드를 펼치면 진행 기록(조기 종료·승격·예산 도달·종료)을 기본 표시. 이전에는 상세 패널에만 있었다 | `GroupProgress` |
| 6 | 반대 근거 | 분석 카드에 반대 근거 건수와 한글 항목, 영문 항목은 요청 시 표시 | `AgentBasis`, API `counter_evidence` |
| 7 | 독립 검증 결과 | 검증 카드에 판정·다음 행동과 후보별 수락 여부·검증 대상·사유 | `VerifyResult`, API `candidate_verdicts` |
| 8 | Runbook·기존 자료 근거 | 그 단계가 인용한 참고 문서의 이름·종류·구획과 발췌. 쓰이지 않던 `CitationLink`를 연결 | `AgentBasis`, API `citations` |
| 9 | 사건당 AI 비용·시간 | 상황 요약에 모델 호출 수, 모델별 호출, 토큰 입력/출력, 비용, 모델 응답 시간 합 | `UsageLine` |

**백엔드(`liveprobe/app/flowgraph.py`)**: 단계 카드에 위 필드를 추가했다. 모두 이미 저장된 기록(에이전트 출력, `escalated` 실행 기록, 인용 테이블)에서 읽으며 새 모델 호출이나 재검증은 없다.

**판단과 한계**
- `ref_known`은 인용이 가리키는 번호가 이 사건에서 수집된 근거(또는 그 단계가 인용한 참고 문서)에 해당하는지만 뜻한다. 인용문이 원문에 그대로 있는지는 엔진의 인용 검사가 실행 시점에 판정하며, 화면은 그 결과를 다시 계산하지 않는다(승격 사유·`acceptance`로 드러난다).
- 참고 문서는 엔진이 "실제로 인용한" 것만 저장한다. 검색됐지만 인용하지 않은 문서는 기록이 없어 표시할 수 없다. 저장 시 R1·R2 번호가 남지 않아 R# 인용을 특정 문서 조각에 묶지 않는다.
- 인용문·영문 사유·영문 반대 근거는 기존 화면 계약대로 요청할 때만 DOM에 넣는다. 기본 표시는 한글 문장과 건수다.
- "고성능 모델 호출 수"는 어떤 모델이 고성능인지의 기준이 화면에 없어 모델별 호출 수로 대신했다.
- 이전 서버 응답(새 필드 없음)에서는 해당 영역을 그리지 않는다. 값을 지어내지 않는다.
- 그룹 카드의 이전 계약("역할 구성은 상세에서만")은 1번 요구에 따라 바꿨고 `tests/p18-w6-room.test.ts`의 해당 시험을 새 계약으로 고쳤다.
- 모의 fixture의 인용문·참고 문서는 실제 에이전트 출력 기록이 아니라 같은 fixture의 원문에서 만든 모의 값이다(`e2e/enrich-p20-fixtures.py` 머리말). 승격 사유는 fixture의 실제 실행 기록이다.

### 3.5 하지 않은 것

- 과제계획서 대조 10번(평가 결과·4개 방식 비교 화면)과 시스템 수준 미달 항목(선택 정확도·비용·자동 복구 목표, 현재 모델 구성 재평가).
- 관제실 내부 마크업을 디자인 시스템 React 컴포넌트(`ChatMessage`·`Composer`·`CodeBlock`·`DiagramNode`)로 교체하는 것. 같은 형태를 스타일로 구현했고, 컴포넌트 교체는 기존 단위·E2E 시험의 마크업 계약을 바꾸므로 하지 않았다.
- 검토 기록·설정 화면의 구조 변경(토큰만 적용).
- 다크 테마, 모바일 전용 재배치.

## 4. 완료 기준

- A1. `npm test`, `npm run build`가 통과한다.
- A2. 모의 API E2E(1440px)에서 리뉴얼 전 main에서 통과하던 시험이 리뉴얼 후에도 통과한다. 의도적으로 바꾼 계약(다이어그램 배경색)은 시험을 함께 고친다.
- A3. 운영 관제 첫 화면에서 스크롤 없이 "운영자 결정이 필요한 장애 수"와 "가장 먼저 볼 장애"를 읽을 수 있다.
- A4. 승인 대기·미인수 인계 장애는 알림, 운영 관제 대기열, 장애 목록에서 분석 중 장애보다 앞에 온다.
- A5. 관제실에서 결정이 필요한 상태면 한 번의 동작으로 결정 카드에 도달한다.
- A6. 값이 없는 집계는 0이 아니라 `미관측`으로 표시한다.
